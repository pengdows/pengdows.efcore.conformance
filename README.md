# pengdows.efcore.conformance

Independent black-box conformance testing for relational EF Core 10 providers. Tests call documented EF Core APIs and assert observable behavior. They do not inspect generated SQL, provider internals, or provider service registrations.

## Architecture and status

- Establish EF Core 10/net10.0 project boundaries.
- Define the provider configuration and database lifecycle contract.
- Load adapters by assembly and type name without compile-time provider references.
- Discover ADO.NET `DataTypes` metadata without assuming provider-specific columns.
- Generate an assembly-derived public API inventory. Contract rules classify EF-owned and provider service APIs with rationale; tested API families take precedence, and remaining provider-applicable members stay uncovered.
- Include Microsoft's SQLite provider as a reference run, so candidate-only failures can be separated from behavior that reproduces on a reference provider.

The inventory generator captures public members from `Microsoft.EntityFrameworkCore`, `Microsoft.EntityFrameworkCore.Abstractions`, `Microsoft.EntityFrameworkCore.Relational`, and `Microsoft.EntityFrameworkCore.Design`. It reads disposition rules from `manifests/efcore-10.json` beside the output file; each non-applicable classification includes its reason. Pass the built relational test assembly as a second inventory argument to link `[BehavioralCoverage]` test contracts to API member families. This family-level link does not claim every overload is independently covered. The runner can execute the shared test project and write JSON and JUnit result reports; test logs and TRX details are sanitized for the configured connection string. Strict runs require adapters to declare every known capability as supported or unsupported. A comparison command classifies matching results as passing on both, candidate-only failures, or failures that also occur on the reference provider.

## Run the initial tools

```sh
dotnet run --project src/pengdows.efcore.conformance.Inventory -- ./manifests/efcore-10-api-inventory.json tests/pengdows.efcore.conformance.EF10.Relational/bin/Debug/net10.0/pengdows.efcore.conformance.EF10.Relational.dll
PENGDOWS_EFCORE_CONFORMANCE_CONNECTION_STRING='...' dotnet run --project src/pengdows.efcore.conformance.Runner -- ./My.Adapter.dll My.Adapter.ProviderAdapter
PENGDOWS_EFCORE_CONFORMANCE_CONNECTION_STRING='...' dotnet run --project src/pengdows.efcore.conformance.Runner -- --discover-types ./My.Adapter.dll My.Adapter.ProviderAdapter ./ado-net-types.json ./path/to/test-assembly.dll
PENGDOWS_EFCORE_CONFORMANCE_CONNECTION_STRING='...' dotnet run --project src/pengdows.efcore.conformance.Runner -- --run tests/pengdows.efcore.conformance.EF10.Relational/pengdows.efcore.conformance.EF10.Relational.csproj ./My.Adapter.dll My.Adapter.ProviderAdapter ./conformance-results
```

Connection strings are read from the environment, not command-line arguments. The solution includes the Microsoft SQLite reference adapter and is buildable without the separate pengdows ADO.NET repository:

```sh
dotnet build pengdows.efcore.conformance.slnx
```

## Provider run profiles

The ADO.NET conformance project’s `providers/*.json` pattern is a good fit for keeping per-database run settings out of shared tests. This EF harness uses smaller JSON profiles because provider setup still belongs in a compiled EF adapter: `adapterAssembly` and `adapterType` select that adapter, and `connectionString` can expand `${ENVIRONMENT_VARIABLE}` placeholders. The adapter remains authoritative for EF provider configuration, database initialization, cleanup, and capability declarations. A profile cannot override capabilities or expected results. Adapters may implement `IParameterizedCollectionModeAdapter` to configure EF Core's public relational collection translation mode for shared behavior tests.

Profiles do not start containers or provision remote databases. Point the profile at a database that is already available, using an environment variable for secrets and machine-specific paths. Adapter assembly paths are relative to the profile file unless absolute.

```sh
dotnet build pengdows.efcore.conformance.slnx
export EFCORE_CONFORMANCE_DB_PATH=/tmp/efcore-reference.db
dotnet run --project src/pengdows.efcore.conformance.Runner -- --run-profile \
  profiles/microsoft-sqlite.json \
  tests/pengdows.efcore.conformance.EF10.Relational/pengdows.efcore.conformance.EF10.Relational.csproj \
  /tmp/efcore-reference-report --cleanup-database
```

`profiles/pengdows-sqlite.json` uses the same shape for the candidate adapter. Build that adapter separately when its sibling ADO.NET repository is available. Direct `--run` commands and `PENGDOWS_EFCORE_CONFORMANCE_CONNECTION_STRING` remain supported.

The optional `profiles/pomelo-mysql.json` profile runs the same EF Core 10 test assembly against MySQL 8.4 through Pomelo. Set `EFCORE_CONFORMANCE_MYSQL_HOST`, `EFCORE_CONFORMANCE_MYSQL_PORT`, `EFCORE_CONFORMANCE_MYSQL_DATABASE`, `EFCORE_CONFORMANCE_MYSQL_USER`, and `EFCORE_CONFORMANCE_MYSQL_PASSWORD` before invoking `--run-profile`. Use a dedicated database: database-lifecycle tests delete and recreate it, and `--cleanup-database` deletes it after the run.

The optional `profiles/npgsql-postgresql.json` profile runs the suite against PostgreSQL 17 through Npgsql. Set `EFCORE_CONFORMANCE_POSTGRES_HOST`, `EFCORE_CONFORMANCE_POSTGRES_PORT`, `EFCORE_CONFORMANCE_POSTGRES_DATABASE`, `EFCORE_CONFORMANCE_POSTGRES_USER`, and `EFCORE_CONFORMANCE_POSTGRES_PASSWORD`. The profile database must allow the configured user to create and drop it because lifecycle tests recreate the database.

Use a dedicated disposable database. Migration and database-lifecycle cases delete and recreate the configured database; the runner’s optional cleanup deletes it after the run. PostgreSQL cleanup verifies through the maintenance database if dropping the active database closes the original connection. An adapter may implement `IAdoNetProviderAdapter` to enable public `DbConnection.GetSchema` type discovery. It may also implement `ISupplementalTypeDiscovery` to report types observed through database catalog metadata when the ADO.NET provider omits `DataTypes`. Native type mapping profiles also require `INativeTypeTableCleanupAdapter`, which removes each isolated table pair after its scenarios. Supplemental discovery is marked `INDEPENDENT` only when it is independent of the EF model. Discovery from tables created by these tests is marked `SELF_DERIVED` and excluded from native-type coverage counts. SQLite does not advertise `DataTypes`; its current-schema type list is self-derived and cannot establish complete database-type coverage.

An adapter can implement `IDatabaseTypeCatalogDiscovery` to report an independent database catalog inventory and compare its names with ADO.NET discovery. The Npgsql adapter reads PostgreSQL’s public `pg_type` and `pg_namespace` catalogs, retaining schema, kind/category, array element, domain base, and composite relation metadata. Its inventory includes system, pseudo, composite, domain, array, and extension types. Scalar-name comparison is scoped to `pg_catalog`; the full catalog snapshot retains other schemas. A live PostgreSQL 17 check observed 469 `pg_catalog` type names against 133 ADO.NET rows: 53 exact matches, 75 normalized alias matches (including PostgreSQL array names and aliases such as `bool`/`boolean` and `int4`/`integer`), 341 catalog names without ADO.NET matches, and five ADO.NET `information_schema` pseudo-domain names without catalog matches. The Pomelo adapter reads MySQL system schemas through `information_schema.COLUMNS`; a live MySQL 8.4 check observed 3,551 catalog columns spanning 23 distinct native type families against 51 ADO.NET `DataTypes` rows. This is an observed catalog-column inventory, not an exhaustive list of every MySQL type accepted by the server. Catalog name differences are discovery evidence, not automatic EF mapping failures; many entries are not scalar EF mapping targets. Catalog comparison remains separate from generated type-fidelity coverage.

The runner does not inspect EF provider internals or generated SQL. For each adapter-declared CLR mapping matched to ADO.NET `DataTypes` discovery, it generates sync and async insertion/readback, update, null, declared decimal-boundary, and scalar parameterized equality-query cases where equality applies. Each mapping runs in an isolated EF model and table namespace, and persistence assertions use fresh EF contexts. Public EF Design tests exercise migration generation, scaffolding, and reverse-engineering model helpers through provider public APIs. The current comparison set includes 478-case SQLite, DuckDB, and SQL Server runs, 738-case MySQL runs, and 1,274-case PostgreSQL runs. Six harness-only discovery and catalog comparison tests are tagged `HarnessUnit` and excluded from provider reports; run them separately with `dotnet test ... --filter Category=HarnessUnit`. Native type mapping tests use independently discovered MySQL and PostgreSQL types; SQLite test-schema discovery is self-derived and excluded from completeness counts.

### Completion criteria

The EF Core 10 milestone is complete when all applicable API contracts have behavioral scenarios with sync and async coverage where both exist; discovered native mappings have independently executed fidelity cases; failures are triaged; and reports separate execution outcomes from static test links. The Design API inventory currently has no uncovered or unclassified members, with explicit rationales for APIs that do not express provider behavior. This does not complete the behavioral matrices. Native mapping coverage is an initial subset, not complete database-type coverage: non-decimal boundary cases and many unlinked discovered types remain.

ADO.NET type discovery preserves raw metadata and, when the provider returns CLR `Type` objects, their assembly-qualified identities. The run report summarizes `DataTypes` availability, duplicate names, missing CLR mappings, and unresolved CLR names. Native type coverage is computed only from independent discovery. When discovery is self-derived, `NativeTypeCoverage` is empty. Independent inventories report `PASS` when all generated sync/async cases for a declared mapping pass, `FAIL` for observed failing cases, `PARTIAL` when only some expected cases ran, `NOT_EXECUTED` when linked scenarios did not run, and `UNLINKED` when no provider mapping profile claims the discovered type. These are runtime results, not static annotations.
